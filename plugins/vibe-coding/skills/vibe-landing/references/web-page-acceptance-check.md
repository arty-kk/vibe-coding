# Web Page Acceptance Check

## Goal

Reconcile the completed homepage/landing result with the original request and implementation packet. Establish which required outcomes are actually built and evidenced, which fail and which remain blocked. Prevent attractive fragments or a green build from hiding omitted content, states, assets or integration work.

## Acceptance boundary

Use the original requirement ledger, accepted decisions, actual artifact/version, changed owners and current domain-check evidence. Keep the comparison boundary and test environment explicit. A bounded component/copy fix validates its affected contract and controls; a complete new page needs complete applicable coverage. Reuse valid existing evidence when its inputs and boundaries have not changed.

## Reconcile every requested outcome

For each requirement, record its actual implementation/artifact, acceptance case and observed result. Distinguish an explicitly required outcome from a conditional suggestion. A required item cannot be silently marked not applicable or replaced by a polished placeholder. Verify the applicable foundations across offer/content, header/hero/sections/footer, brand/icons/media, type/palette/geometry/surfaces, components/states, meaningful navigation, functional modules/motion/fallbacks, responsive/accessibility behavior, modular architecture, search and loading.

Check the delivered page as a whole after individual checks. Follow the primary and secondary visitor paths from entry to their useful outcomes and recovery. Use real strings, assets and representative narrow/wide/short-height conditions. Confirm the page retains the intended visual character and professional copy instead of merely containing all expected headings.

Inspect the actual workspace/build output and declared asset/configuration paths. Confirm required logos/favicons, content, routes, controls and state variants exist and are integrated; source filenames alone do not establish that the page uses them. Real effects need the relevant authorized integration/persistence/recipient evidence. A local test adapter, generated study or optimistic message cannot stand in for production behavior.

Reconcile applicable results from **Web Visual Hierarchy & Geometry**, **Web Navigation & State**, **Web Interaction & Motion** and **Web Search & Performance** checks. A known failure remains failed; unobserved required behavior remains blocked. Do not invent a check result, hide an unresolved integration in a limitation paragraph while declaring the whole site ready, or count screenshots as proof of delivery or runtime lifecycle behavior.

The local packet-coverage helper may confirm requirement-ID and artifact/evidence presence when a structured packet is used. Its result is structural evidence, not a verdict on the page's aesthetics or correctness. Review the actual underlying artifacts and outcomes.

## Verdict and completion

Return a concise requirement/result matrix, delivered artifacts, actual verification, failures and concrete remaining gates. Use `passed` only when every required criterion in the stated scope has evidence. For a prototype or local-only request, do not add a production deployment requirement; identify the genuine boundary of the result.

For an authorized build/repair, return a failure to its owner, repeat affected acceptance after correction, then finish repeated **Patch Checking** against the original base. Patch review does not override a failed domain criterion. Publication is a separate action governed by the actual request and host permissions; report it independently of build/acceptance status.
