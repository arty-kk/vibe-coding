# Web Experience Brief

## Goal

Assemble the current offer, page narrative, finished copy, references, brand assets, visual/interaction system and technical architecture into one coherent implementation packet. Identify omissions and contradictions before a builder starts. The packet must permit concrete implementation decisions without re-inventing the project.

## Reconcile the inputs

Read the original request and preserved requirement ledger, then the actual outputs of completed stages. Reuse accepted project material. Recover a missing ordinary decision from the current evidence; select a coherent proposal when the user left creative room. Load the focused missing workflow when a substantive stage is genuinely absent. Do not treat the presence of a heading or a planned filename as a completed deliverable.

For every explicit requirement, retain its stable ID, intended result, responsible stage/owner, decision, artifact and acceptance evidence. Distinguish required outcomes from conditional suggestions. Carry constraints and unresolved facts forward verbatim enough to preserve their meaning. An explicit requirement cannot silently become optional because another section or framework is easier to build.

## Implementation packet

Provide the following applicable contracts with actual values and references:

| Area | Builder-ready contents |
|---|---|
| Offer and funnel | Audience/arrival context, offer, proof, primary/secondary actions and expected commitment |
| Page and navigation | Ordered section jobs, route/anchor map, header/footer groups, meaningful destinations and recovery paths |
| Copy | Exact visible strings by section/state, glossary, variables/count forms, factual sources and separate internal content gaps |
| References and assets | Inspected sources and adapted principles; real files, roles, rights/status, crops/variants and acquisition/production tasks |
| Brand | Actual or specified logo variants, small-size mark, favicon/touch/app/sharing exports and integration map |
| Visual system | Complete type roles, palette, grid/spacing/section rhythm, surfaces, borders, shadows, transparency, gradients, icon/media rules and component states |
| Composition and geometry | Hero scale/height behavior, section variation, transitions, alignment axes, internal spacing/baselines, optical exceptions and responsive reflow |
| Interaction and motion | Functional state contracts, trigger/feedback/recovery, durations/easing, useful effects, no-JavaScript/reduced-motion/static paths and lifecycle limits |
| Technical architecture | Actual stack/support rationale, modular workspace tree, import/rendering boundaries, content/data/integration owners and commands |
| Search and loading | Route/metadata/canonical/locale/schema/crawler strategy, current provider controls, asset and execution budgets, measurement plan |
| Acceptance and release | Requirement-to-case mapping, normal/failure/keyboard/responsive scenarios, delivered artifacts, actual evidence and remaining gates |

Preserve page-specific creative decisions. “Add modern animation”, “use premium glass” or “make the typography good” needs a concrete composition, parameters, states and acceptance case before it is a build instruction. Check mutual consistency: real copy fits the intended hierarchy, background/material states preserve text, navigation promises available content, the stack can deliver the storyboard, and budget decisions include actual assets.

## Coverage check

Use a compact matrix to reconcile every requirement with its resolution and artifacts. For a substantial packet, [the local coverage checker](../scripts/check_web_packet.py) can compare the preserved requirements JSON with a candidate packet and verify declared local artifacts. Its format and example are described in the helper's module docstring and `--help`. It checks structural coverage and declared evidence presence; it cannot establish tasteful design, grammatical correctness, working delivery, search inclusion or performance by reading a report.

Treat a missing required decision or artifact as an explicit gate. A specified integration contract may complete a proposal while its real configuration remains an implementation/release dependency. A request to build a working integration is not satisfied by that specification. Do not replace missing projects or real customer proof with polished placeholders, or mark unavailable browser/device/recipient evidence as passed.

## Completion and handoff

Return the consolidated packet, coverage matrix and any concrete remaining decisions/artifacts. Use the task's requested format or maintained project specification; do not scatter contradictory copies across new documents. A builder must be able to identify its current implementation slice, sources, acceptance cases and unresolved production dependencies.

The proposal ends here when implementation was not requested. For an already-requested build, hand the packet to **Build Homepage & Landing Page**. Retrieve the implementation prompt only when that transition is authorized; a planning sequence does not itself create permission to edit or deploy.
