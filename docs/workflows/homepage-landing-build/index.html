Goal

Implement the requested public homepage or landing experience as a complete, coherent, responsive and usable site. Carry its offer, original visual direction, real content/assets, components, interactions, architecture, search and loading requirements through to observable acceptance. A hero, repeated feature cards and unconnected buttons do not complete the requested site.

Establish the build boundary

Read the actual request, repository/project rules and current implementation packet. Preserve a usable existing stack, accepted brand, content and working behavior. Start directly from a sufficiently defined target; do not force a complete strategy process onto a known build or bounded fix. When essential upstream decisions are missing, obtain the focused offer, copy, design or architecture method and continue independent work while genuine factual gates are resolved.

Retain the original requirement ledger. Define the requested route(s), deliverable, necessary integrations, accepted visual/composition rules and measurable acceptance cases. Differentiate a production build from an explicitly requested prototype. An illustrative dataset or test adapter must not become a claim about a real business or delivered enquiry.

Establish the visual relationship

For a new homepage or a broad redesign, carry the user's visual preferences and intensity limits into a small rendered slice. Inspect the opening and its primary action on desktop and on a narrow phone before repeating the design. Use the actual copy and media. Decide what should stand out, where the light comes from, and which visible cue separates each important surface.

Treat a request for shadows, contours or glass as a relationship between layers. Choose one dominant cue per boundary. For example, give a raised panel a soft external shadow and a faint upper reflection, and give its inner prompt a darker fill with a shallow inset shadow. Use line contrast where a divider or control needs it. Keep ordinary surfaces quiet and reserve the strongest accent for the primary action or current state. Inspect the sum of the treatments at normal scale and remove cues that repeat an effect the fill, light or shadow already provides.

Build the experience

  1. Establish the selected modular workspace, actual package/runtime versions, rendering boundaries, content/token ownership and working commands. Create the needed structure rather than empty speculative packages. Keep app sections, shared primitives, domain rules and server adapters at their intended owners.
  2. Implement the page's real content and primary path early enough to expose missing facts and destinations. Keep exact approved copy in its maintained content/locale layer. Do not put designer instructions, filler headings, placeholder proof or implementation notes into visitor-facing strings. Use the actual text lengths when composing the page.
  3. Build the visual system and primitives: containers/grid, typography roles, semantic palette, spacing, surfaces/elevation, borders/focus, buttons/fields, icons and media. Apply them through explicit component APIs and state variants. Check the actual font files/weights/glyphs and relevant color pairs; numerical weight order is not a hierarchy test.
  4. Compose header, hero, each selected narrative/functional section and footer as designed. Let section content determine height and adapt the hero to available height without cropping copy/actions. Vary compositions by their content while retaining common alignment and detail rules. Inspect internal geometry: padding rhythm, text baselines, media bounds, icon optical alignment, nested radii and repeated action placement. Preserve intentional asymmetry from the direction.
  5. Integrate actual logo/favicons/touch/sharing assets and the chosen real media. Preserve intrinsic sizes and responsive crops. Use purposeful original diagrams or procedural materials when appropriate, with quiet reading areas. Keep real product/customer evidence distinct from illustration; a stock image or abstract volume is not a completed project photograph.
  6. Implement selected modules to their actual contracts: useful menus/routes, forms, lead magnets, calculators/configurators, pricing, galleries, maps or promotions. All visible actions need meaningful destinations or effects. Verify complete input/pending/result/error/recovery behavior, correct quantities/units, acknowledgement and relevant duplicate handling. A placeholder handler, href="#", fake success toast or merely existing anchor cannot satisfy the conversion path.
  7. Apply the storyboard's motion and material treatments. Preserve useful content on first render, normal scroll/focus, reduced-motion/static behavior and touch/keyboard equivalents. Bound and pause procedural/3D work, clean up resources and use a feasible fallback. Check glass, gradients, shadows and outlines in their actual foreground/background/state relationships.
  8. Implement the route's search and loading design at its owner: meaningful server/static content, real title/description/social image, canonical/locale relationships, sitemap/robots, accurate supported structured data and appropriate staging/public controls. Prioritize the real LCP asset, reserve media space, limit client JS/fonts/third-party work and load noncritical effects when useful.

Verify and finish

Use actual repository commands and bounded tests. Walk the conversion and navigation paths with normal, invalid, unavailable and recovery cases. Render the complete page at representative narrow/wide and short-height viewports, with actual copy/assets and relevant themes. Compare the complete composition as well as component details; attractive isolated fragments do not establish a coherent page.

Run the applicable Web Visual Hierarchy & Geometry, Web Navigation & State, Web Interaction & Motion, Web Search & Performance and Web Page Acceptance checks. Return a failure to the owning implementation and repeat affected checks. Keep unavailable required production inputs or evidence open. Then perform repeated Patch Checking against the original comparison base; a clean marker requires an actual unchanged final review pass.

Report what is built, the actual checks and artifacts, any remaining production gates and publication status. A local build, prototype, screenshot or retrieved method is not a deployed site or proof of real user conversion. Deploy only within the actual requested scope and host permissions.
